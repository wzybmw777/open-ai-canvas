# 本地开发

## SMTP 邮件故障日志

注册、登录、绑定邮箱和密码找回的邮件投递失败统一输出 `ERROR` 级别的 `smtp email delivery failed` 后端日志。日志包含 `host`、`port`、`encryption`、脱敏 `recipient` 和 `error`，默认 `CANVAS_LOG_LEVEL=info` 即可看到，无需开启 debug。

`error` 保留 SMTP 状态码和服务器错误说明，并标记失败步骤：`connect` / `connect_tls`（连接）、`greeting`（服务器欢迎响应）、`starttls`、`auth`、`mail_from`、`rcpt_to`、`data`、`write_body`、`finish_data` 或 `quit`。日志不主动记录账号、密码、邮件标题、正文或验证码，并对错误中回显的这些值及其 Base64 编码做脱敏。对外 API 继续使用原有通用错误响应。

宿主机开发查看运行后端的终端；Docker 查看实际使用的 Compose 文件中的 `backend` 服务，例如：

```bash
docker compose -f docker-compose.deploy.yml logs --since=15m -f backend
```

本地构建和热更新开发分别将文件名换成 `docker-compose.local.yml` 或 `docker-compose.dev.yml`。代码修改后需要运行新构建的后端，旧容器不会自动增加这些日志。

## Compose 公网资源地址

`docker-compose.yml`、`docker-compose.dev.yml`、`docker-compose.local.yml`、`docker-compose.server.yml` 和 `docker-compose.deploy.yml` 均将 `.env` 中的 `CANVAS_PUBLIC_BASE_URL` 传入后端。使用本地文件存储且上游模型需要读取参考素材时，将它设为上游能访问的 HTTPS 站点根地址（例如 `https://canvas.example.com`，不要附加 `/api`）；存储设置中的公网访问地址优先于该环境变量。

修改后需要重新创建后端容器，单纯重启旧容器不会更新环境变量。未配置时保持空值并由资源请求强校验，不会自动采用容器内网地址；这项设置不放宽出站 SSRF 校验，也不应为此开放数据库或后端端口。只做本地界面开发且不向模型提交资源时可以不设置。部署后仍需验证真实资源 URL 能被目标供应商读取，健康检查不能替代该验证。

## 一键启动（Windows PowerShell）

在仓库根目录执行：

```powershell
.\scripts\start-local.ps1
```

脚本会：

- 使用 `.local/project-workbench-debug` 作为后端 SQLite 开发数据目录；
- 创建 `.local/cache/go-build` 和 `.local/cache/go-mod` 缓存目录；
- 首次启动时，如果 `web/node_modules` 不存在，执行 `bun install --frozen-lockfile`；
- 打开两个 PowerShell 窗口，分别运行后端和前端；
- 将前端 `/api` 请求代理到 `http://127.0.0.1:8080`。

启动后访问 [http://localhost:3000](http://localhost:3000)。后端健康检查地址是 [http://127.0.0.1:8080/api/health](http://127.0.0.1:8080/api/health)。

脚本使用固定的本地开发端口：前端 `3000`，后端 `8080`。如果端口被占用，脚本会先退出，不会关闭已有进程。请分别在两个开发窗口中按 `Ctrl+C` 停止服务。

如果 PowerShell 的执行策略阻止脚本运行，可以只对当前进程临时放行：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start-local.ps1
```

## 手工启动

后端：

```bash
mkdir -p .local/project-workbench-debug .local/cache/go-build .local/cache/go-mod
cd backend
CANVAS_BACKEND_ADDR=127.0.0.1:8080 \
CANVAS_BACKEND_DATA_DIR=../.local/project-workbench-debug \
GOCACHE=../.local/cache/go-build \
GOMODCACHE=../.local/cache/go-mod \
go run ./cmd/server
```

前端另开终端：

```bash
cd web
bun install --frozen-lockfile
bun run dev
```

`web/` 只使用 `bun.lock`。不要用 pnpm 或 npm 往同一套 `node_modules` 里再装一遍。

前端默认监听 `0.0.0.0:3000`，Vite 将 `/api` 和 OAuth 回调代理到 `127.0.0.1:8080`。如需修改代理目标，可设置 `VITE_API_PROXY_TARGET`。

## 时间线字幕转写（whisper.cpp）

时间线“字幕转写”由**本地 whisper.cpp server** 执行：后端将片段音频预处理为 16k mono wav 后，POST 到 `CANVAS_WHISPER_BASE_URL/inference`（whisper server 原生接口，`response_format=verbose_json`）。未配置该地址时，转写任务会立即明确失败，提示“撰写失败未配置本地转写服务”。

### 安装 whisper-server

```bash
brew install whisper-cpp
```

### 下载模型

仓库脚本将模型放在 `.local/whisper-models/`（已被 `.gitignore` 忽略）。多语言模型（含中文）用 `ggml-base.bin`（约 141MB）；网络受限时可用 aifasthub 镜像：

```bash
mkdir -p .local/whisper-models
curl -fL -o .local/whisper-models/ggml-base.bin \
  https://aifasthub.com/ggerganov/whisper.cpp/resolve/main/ggml-base.bin
```

### 启动服务

```bash
scripts/start-whisper-local.sh
```

脚本默认以 `ggml-base.bin` 监听 `127.0.0.1:8082`（`-l auto` 自动识别语言）。需要换模型或端口时：`WHISPER_MODEL=ggml-small.bin WHISPER_PORT=8083 scripts/start-whisper-local.sh`。

### 让后端指向该服务

后端不读取 `.env` 文件，环境变量必须由启动 shell 注入（在手工启动命令基础上追加）：

```bash
cd backend
CANVAS_BACKEND_DATA_DIR=../.local/project-workbench-debug \
CANVAS_WHISPER_BASE_URL=http://127.0.0.1:8082 \
go run ./cmd/server
```

### 验证

```bash
# 服务就绪：返回 200/404 即可
curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8082/
# 冒烟：20 秒语音 → verbose_json 字幕段
curl -s -X POST http://127.0.0.1:8082/inference \
  -F 'file=@sample.wav' -F 'response_format=verbose_json'
```

## Docker 开发

需要容器化热更新时，在仓库根目录执行：

```bash
LOCAL_UID=$(id -u) LOCAL_GID=$(id -g) \
  docker compose -f docker-compose.dev.yml up --build
```

Docker 开发编排也使用 `.local/project-workbench-debug`，并默认暴露前端 `3000` 和后端 `8080`。端口冲突时，可通过 `CANVAS_WEB_HOST_PORT` 和 `CANVAS_BACKEND_HOST_PORT` 调整宿主机端口。

## 服务器源码热更新

源码安装脚本默认使用生产数据编排叠加 `docker-compose.hot.yml`。前端挂载仓库并由 Vite 监听，后端挂载仓库并由 Air 监听；保存 `web/src` 或 `backend` 下的源码后，服务会自动重新加载。PostgreSQL、Redis、Agent 和 `/data` 仍由 `docker-compose.deploy.yml` 管理。

```bash
cd /opt/open-ai-canvas
docker compose --env-file .env \
  -f docker-compose.deploy.yml -f docker-compose.hot.yml \
  up -d --build --remove-orphans --wait --wait-timeout 600
```

首次切换或修改 `backend/Dockerfile.dev` 时会构建一次热更新运行时镜像；日常源码修改不重新构建镜像。Agent 仍按独立镜像运行，需要变更 Agent 运行时代码时单独构建。只有推送 `v*` 标签或手动运行发布工作流才会发布镜像。

## 增量构建发布镜像

小改动优先使用持久化构建入口，避免每次同时重建前后端：

```bash
# 默认 auto：按各镜像输入选择需要构建的单元
bash scripts/build-images.sh

# 明确执行某个镜像构建，仍复用 Docker 与 Go 缓存
bash scripts/build-images.sh web
bash scripts/build-images.sh backend

# 强制执行两个镜像构建
bash scripts/build-images.sh all
```

`auto` 对比镜像标签 `org.yingce.build.inputs` 与源码输入指纹，识别已提交、未提交、新增和删除的文件。只改 `web/src` 不执行后端构建，只改后端不执行前端构建；文档站内容不参与业务镜像构建。`README.md` 与 `CHANGELOG.md` 被前端实际读取，因此修改它们仍会更新前端。镜像缺失或没有指纹标签时先构建一次；输入未变则直接复用本地镜像，省去镜像导出。显式设置 `BUILD_VERSION`、`BUILD_COMMIT` 或 `BUILD_TIME` 会参与判定，默认 Git 提交号与时间只用于构建信息。

Agent Node 依赖镜像仅在依赖清单、锁文件或依赖 Dockerfile 变化、镜像缺失时重新构建；它仍是生产后端的独立依赖。此脚本只构建镜像，不修改正在运行的容器，也不会替代 Compose 中的 `yingce-agent` 服务。

后端 Dockerfile 只读挂载编译源码，避免把整份后端再复制进中间层；主程序和两个迁移工具用一次 `go build` 输出，减少重复解析依赖。支付插件只挂载其依赖的 SDK、支付实现和五个命令入口，普通业务修改不会触发五个插件重编译；插件打包、架构校验及运行冒烟仍保留。Go 模块和编译缓存采用可并发共享的持久化挂载，编译临时对象使用内存挂载。主程序保留 SQLite 所需的 `CGO_ENABLED=1`。最终镜像先复制插件与 Agent 文件，最后复制业务二进制，普通后端修改只替换最后的二进制层。

服务器默认 `GO_BUILD_PARALLELISM=2`，限制包编译并发，避免编译挤占线上服务资源。资源充足时可按实际内存和磁盘吞吐调整：

```bash
GO_BUILD_PARALLELISM=4 bash scripts/build-images.sh backend
```

使用同一个 Docker `default` Builder，不清理 Go、模块或 Docker 缓存。缓存命中不代表编译一定瞬时完成：代码变化仍需编译和链接，前端代码变化仍需 Vite 构建，镜像导出也受磁盘吞吐影响。首次安装或缺少缓存时会完整构建。构建期间输入变化会明确失败，重新执行即可；构建选择逻辑可用 `python3 scripts/test_build_images.py` 验证，Python 仅用于该测试，发布脚本不依赖 Python。
