# 源码更新提速 Implementation Plan

> 使用 executing-plans 在当前会话直接实现，专项测试先行。

**Goal:** 缩短已启用的源码更新流程，继续保留本站定制、备份、迁移、健康验证和失败回退。

**Architecture:** 根据更新前提交与预合并提交的真实文件差异生成构建计划；源码部署由 Vite 提供页面，因此保留前端类型检查，取消不被运行服务使用的生产打包。仅在依赖或镜像输入变化时重新安装/构建，其他情况复用当前固定镜像。

**Tech Stack:** Go、Git、Bun、Docker Compose。

**Spec:** 用户要求系统更新更快；沿用已选择的源码合并模式。

## 边界

- 不减少备份、迁移、运行提交核对与稳定窗口，不执行真实上游更新。
- 变更检测覆盖删除与改名、Agent 运行时、Dockerfile、Go 依赖、Compose 与 Docker 上下文规则；共享配置变化采取保守重建。
- 前端源码变化仍做类型检查；锁文件/安装配置变化或依赖缺失时执行冻结安装；原锁文件的依赖缓存预热保留，回退仍恢复原锁文件。
- 只有实际构建的镜像设置新标签；未构建的服务继续使用固定的旧镜像 ID。

- [x] 用真实 Git 仓库补充增量计划测试，覆盖纯文档、前端、依赖、后端基础镜像、Agent、共享 Compose、删除和改名。
- [x] 实现构建计划及实际执行，测试未变更镜像不被重建/改标签，前端仅做类型检查，缺失依赖仍安装，错误仍触发原回退路径。
- [x] 更新专题与待测试文档，运行 hostupdate 专项测试、编译和独立审查。
- [x] 本次提交保存优化；新版宿主机更新器已安装，服务二进制、更新器连接和网站健康已实测；不执行实际上游更新。
